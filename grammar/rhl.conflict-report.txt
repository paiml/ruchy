HOW THE CONTROL DISCRIMINATES A CONFLICT FROM ANY OTHER ERROR
    CORRECTION, 2026-09-20. An earlier revision of this file asserted that
    LALRPOP "renders both a conflict and a mere typo as the generic string
    'invalid data'", and built a three-way differential to work around that.
    A second-family review measured the claim and it is FALSE. On lalrpop
    0.23.1, the rendered error does discriminate:

        the fixture, a real LR conflict        ->  "invalid data"
        the same file, undefined nonterminal   ->  "no definition found for `X`"
        the same file, unbalanced delimiters   ->  "unterminated code block; ..."

    "invalid data" is specifically the conflict path. So the gate now asserts the
    error EQUALS that string, which is a direct check rather than an inference.

    The differential is kept as a second, independent leg, because on its own it
    was shown to be insufficient — a fixture whose marked line is an undefined
    nonterminal rather than an ambiguity satisfies all three of its conditions:

        grammar/rhl.lalrpop                       -> Ok
        grammar/fixtures/ambiguous.lalrpop        -> Err
        the same fixture, with the single planted
        production deleted and nothing else       -> Ok

    Together the two legs say: the fixture fails, it fails for an LR conflict,
    and it is the marked line that causes it. Either alone is weaker than this
    file previously claimed.

WHAT THIS REPORT DOES NOT ESTABLISH
    Conflict-freedom is a property of the empty language too. This report says
    the grammar has no LR conflict; it does not say the grammar describes RHL.
    Two gate tests put a floor under that — one requires `Program` to be the
    single `pub` entry point (LALRPOP only builds states for what the entry
    point reaches), the other requires every §3.3 keyword to appear in a
    production and not merely in the lexer's `match` block. Both were added
    after a review demonstrated grammars that passed every other check while
    being unable to parse a single RHL program.

    The real check — that every committed corpus program parses, and parses
    exactly once — needs a generated parser. That is row RHL-1's work, and it is
    named as a gap in docs/audits/impl-RHL-0-receipt.md.
